# Task Tracker API: Go + gRPC-Gateway

Учебный сервис задач с отдельными слоями транспорта, бизнес-логики и хранения.
**Одна команда запускает gRPC-сервер и HTTP Gateway.**

## Запуск

```bash
go run ./cmd/server
```

- HTTP: `http://127.0.0.1:8080`
- gRPC: `127.0.0.1:50051`
- `Ctrl+C` запускает корректное завершение обоих серверов.

Перед первым запуском останови старые процессы `cmd/server` и `cmd/gateway`, если они занимают эти порты.
Другие адреса можно задать флагами:

```bash
go run ./cmd/server -grpc-addr 127.0.0.1:50052 -http-addr 127.0.0.1:8081
```

Хранилище при старте пустое. Данные живут только в памяти и исчезают после перезапуска.
Встроенной задачи с ID `1` больше нет: сначала создай задачу.

## Как проходит запрос

```text
HTTP-клиент (curl)
        ↓ HTTP/JSON :8080
Gateway — сгенерированные HTTP-обработчики
        ↓ настоящий gRPC-вызов :50051
TaskHandler — переводит Protobuf в модель приложения
        ↓
TaskService — проверяет данные и выполняет операцию
        ↓
TaskRepository — читает и изменяет данные в памяти
```

Прямой gRPC-клиент обращается сразу к `TaskHandler`, минуя Gateway.
Gateway и gRPC-сервер работают в одном процессе, но общаются через локальное gRPC-соединение.
Отдельная программа `cmd/client` нужна только для проверки прямого вызова; запускать её постоянно не нужно.

## Где какой код

```text
cmd/
  server/main.go                флаги, сигналы, запуск приложения
  client/main.go                необязательный пример gRPC-клиента
internal/
  app/app.go                    сборка зависимостей и жизненный цикл серверов
  domain/task.go                обычная Go-модель Task и ошибки
  service/task.go               бизнес-правила и интерфейс репозитория
  repository/memory/task.go     реализация репозитория на map + RWMutex
  transport/grpc/task.go        реализация RPC и перевод ошибок в gRPC-коды
proto/
  task/v1/task.proto            контракт API и HTTP-маршруты
  google/api/                  локальные исходники HTTP-аннотаций Google
gen/task/v1/                   сгенерированный код; вручную не менять
```

Интерфейс `TaskRepository` объявлен в сервисном слое: сервис задаёт необходимые ему операции.
Он не знает, хранит ли репозиторий задачи в map или PostgreSQL.
`domain`, `service` и репозиторий не импортируют gRPC или Protobuf.
В `app` зависимости собираются явно:

```go
repo := memory.NewTaskRepository()
taskService := service.NewTaskService(repo)
handler := taskgrpc.NewTaskHandler(taskService)
```

При добавлении PostgreSQL нужно реализовать тот же интерфейс и заменить создание репозитория в `app`.
Транспортные обработчики и контракт API из-за смены хранилища менять не потребуется.

## Проверка HTTP API

Успешные операции сейчас возвращают HTTP **200**, включая создание и удаление.
Это стандартное поведение Gateway в данной конфигурации; удаление возвращает `{}`.
Примеры с ID `1` предполагают первое создание после запуска.

### Создать

```bash
curl -i -X POST http://127.0.0.1:8080/v1/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"Изучить архитектуру","description":"Проследить запрос от Gateway до репозитория"}'
```

Ответ содержит присвоенный сервером `id`. Используй его в следующих запросах.

### Получить и посмотреть список

```bash
curl -i http://127.0.0.1:8080/v1/tasks/1
curl -i http://127.0.0.1:8080/v1/tasks
```

Список имеет форму `{"tasks":[...]}` и отсортирован по числовому ID.
Пустой список — `{"tasks":[]}`. Поле `completed` выводится и при `false`.

### Завершить

```bash
curl -i -X POST http://127.0.0.1:8080/v1/tasks/1/complete
```

Повторное завершение безопасно: задача остаётся выполненной, ответ успешный.

### Удалить

```bash
curl -i -X DELETE http://127.0.0.1:8080/v1/tasks/1
```

Повторное удаление или получение удалённой задачи вернёт 404.

| RPC | HTTP |
|---|---|
| CreateTask | POST /v1/tasks |
| GetTask | GET /v1/tasks/{id} |
| ListTasks | GET /v1/tasks |
| CompleteTask | POST /v1/tasks/{id}/complete |
| DeleteTask | DELETE /v1/tasks/{id} |

## Проверка прямого gRPC

При работающем сервере:

```bash
go run ./cmd/client
```

Клиент запрашивает список по gRPC и печатает задачи. При пустом хранилище напечатает `Tasks: 0`.
Для другого адреса: `go run ./cmd/client -addr 127.0.0.1:50052`.

## Правила и ошибки

- Пробелы по краям заголовка удаляются. Заголовок: 1–200 Unicode-символов.
- Описание: до 2000 Unicode-символов.
- ID выдаёт репозиторий, значения растут последовательно в пределах одного запуска.
- Пустой ID и неверные поля → `InvalidArgument` / HTTP 400.
- Отсутствующая задача → `NotFound` / HTTP 404.
- Неизвестная внутренняя ошибка логируется; клиент получает `Internal` / HTTP 500 без внутренних подробностей.
- HTTP-запрос получает контекст с таймаутом 3 секунды. Размер HTTP-тела ограничен 1 MiB.
- Репозиторий защищён от гонок. Изменение состояния задачи выполняется под блокировкой, наружу возвращаются копии.

## Генерация и тесты

```bash
make generate
make build
make test
```

Эквивалентные команды:

```bash
export PATH="$(go env GOPATH)/bin:$PATH"
buf generate --path proto/task
go build ./...
go test -race ./...
```

`--path proto/task` генерирует только наш API. Файлы `proto/google/api` используются как импорты.
`buf dep update` не нужен: зависимости Protobuf лежат локально (ранее удалённый реестр возвращал 403).
Для восстановления инструментов с версиями, использованными в этом проекте:

```bash
go install github.com/bufbuild/buf/cmd/buf@v1.72.0
go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.12
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@v1.6.2
go install github.com/grpc-ecosystem/grpc-gateway/v2/protoc-gen-grpc-gateway@v2.30.0
```

Интеграционный тест поднимает настоящие gRPC/HTTP-серверы на свободных локальных портах.
Проверяет создание через HTTP и чтение через gRPC, завершение, удаление, ошибки,
параллельные запросы и остановку приложения. Сервисные тесты проверяют границы валидации,
отмену операций и независимость возвращённых данных от хранилища.

## Как изучать код

1. Открой `internal/domain/task.go`: это данные без сетевых деталей.
2. Открой `internal/service/task.go` и найди `Create`: здесь правила создания задачи.
3. Открой `internal/repository/memory/task.go`: здесь задача получает ID и попадает в map.
4. Открой `internal/transport/grpc/task.go`: здесь запрос Protobuf превращается в вызов сервиса.
5. Открой `internal/app/app.go`: здесь все части соединяются, запускаются и останавливаются.
6. Сопоставь RPC из `proto/task/v1/task.proto` с HTTP-запросами выше.

Это законченная учебная архитектура. В ней пока нет постоянного хранения, авторизации,
TLS и пагинации: список возвращает все задачи. Локальные адреса и соединения без TLS рассчитаны на обучение.
